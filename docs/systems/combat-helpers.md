# Immediate GAMERAM combat helpers

The three complete immediate helper bodies are
**912 code bytes** at `0x003fc670`, `0x003fc6f0` and `0x003fc780`.
The 132-byte [technique-row lookup](../../src/game/beNDMWGameRam.cpp)
is C; the 652-byte query and 128-byte deleting destructor share one
[C++ compiler unit](../../src/game/beNDMWGameRam_CollectNearbyNonzeroHp.inc), compiled together with the
[player stat recompute](../../src/game/beNDMWGameRam.cpp).

The separate FightCom metadata builder and BLT attribute accessor are
140 bytes; see the
[compiler requirements](../engine/unit-compilers.md).

| Address | Bytes | Semantic name | Role |
| --- | ---: | --- | --- |
| `0x3fc670` | 128 | `ObjectRef_Destruct_003fc670` | Release a held object and optionally delete its wrapper |
| `0x3fc6f0` | 132 | `beNDMWGameRam_FindTechniqueRow` | Map a WAZALIST base number to its current database row |
| `0x3fc780` | 652 | `beNDMWGameRam_CollectNearbyNonzeroHp` | Gather group members within radius 30 whose HP query is nonzero |

Names are generated by [seed_names_combat_helpers.py](../../scripts/seed_names_combat_helpers.py).
They describe recovered behavior, not claimed original method spelling. These
are complete real functions, unlike FIGHTCALC's interior switch targets.

## Technique row

The player folder's `WAZALIST` property contains an object-reference list.
Each `beNDMWItemWaza` has `_recNo` at +12 and `_baseNo` at +20, independently
named by the reflected fields. The helper walks the cached signed count and
four-byte buffer references. The first matching base number writes `_recNo` to
the output word and returns. Empty/negative counts or no match leave the output
unchanged. Duplicate keys therefore select the first item.

The actual incoming `a0` receiver is unused; player, base number and output
occupy `a1`, `a2` and `a3`. Incidental integer return-register contents are not
part of its void signature.

The matching body uses generated `igObjectList::_count`/`_data` and
`beNDMWItemWaza::_baseNo`/`_recNo`. A natural indexed loop produces the original
initial signed comparison and pointer induction. Declaration order preserves
the register allocation; comparing the key first preserves the original branch
operand order. The content-pinned alternate compiler with `-O3,p` reproduces all
132 bytes and all three relocations. No original local-variable or template
spelling is asserted.

## Nearby group query

The helper allocates an int list, asks the supplied group for `GETMATRIX`, and
caches the returned integer count. For each index it obtains the corresponding
id and matrix, except the explicitly excluded id. Matrix translation is copied
to a three-float temporary, then the center is subtracted in x/y/z order.

Squared distance uses the original operation order: y² and x², their accumulator
sum, then z² plus that sum. Only a strict result below `900.0f` proceeds, so an
exact radius of 30 is excluded. For each admitted member it:

1. Pushes the messenger argument context.
2. Selects the supplied group and id.
3. Sets run-check to one and dispatches `GETHP`.
4. Appends the id when the integer result is nonzero.
5. Pops the argument context.

Negative HP results also pass the nonzero test. Order and duplicate ids are
preserved. Growth reloads the list buffer afterward, including relocation.
Messenger fields are reloaded between services; a replacement made by a service
is observed by subsequent calls.

Result storage receives the list reference, retains it, and releases local
ownership. Destruction tests the low 23 reference-count bits after the full word
decrement. The helper explicitly returns zero in `v0`. Its arguments occupy
output `a0`, receiver `a1`, group `a2`, excluded id `a3` and center `t0`.
The C++ object-return projection now reproduces all 652 bytes and all 23
relocations, including the 256-byte frame. The natural indexed loop places
component-address lifetimes inside the admitted-member branch. Count reloads
remain explicit in the projection. Original class, template and qualifier
spellings are not asserted.

The same compiler unit emits the complete 128-byte deleting destructor at
`0x3fc670`. It releases the held object using the low-23-bit rule, invokes the
delete entry when its signed low-16-bit deletion flag is positive, and returns
the wrapper pointer. The delete symbol has an explicit binding to `0x100610`.

[Explicit emitted-function ownership](../engine/emitted-functions.md) verifies
both complete bodies before placing either one;
no extra code is ignored. The symbol reader correctly handles compiler binding
13. Exceptions are disabled for this compiler unit to suppress new unplaced
metadata; the original retail data remains in the layout.

## Limits

`0x3fc74c` is a reviewed zero alignment word after an unconditional jump; the
row/query pair has 195 executable words.

Property lookup, allocator/factory, list growth/destruction and messenger
services are separate dependencies. Appending after an allocation failure,
MMU fault behavior and arbitrary aliases into compiler scratch storage are
not established. The engine's other dependencies remain separate work.

The full [combat calculation callback](combat-damage.md) matches as
`src/unmatched/Gap__Bec__beNDMWGameRam__vfunc_34.cpp`; the three
completed immediate helpers do not complete the combat module.
