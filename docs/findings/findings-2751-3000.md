### #2756 · refuted

**Where:** 0x0038b1f0 — beMatCtrl update matching, ten-word main-body gap

The changed-contact-bit scan in beMatCtrl::vfunc_31 is a natural for loop over the four bits that breaks after the first changed bit, with the current and previous list words read directly (or hoisted by the compiler) instead of the goto-shaped candidate loop.

**Notes:** Retail does exit the bit loop after the first changed bit (the changed path ends with an unconditional branch to the outer-loop increment at 0x38bc58, the unchanged path increments the bit and branches back to the shift at 0x38ba58), and the two words are loaded once before that loop. Compiling that shape under the pinned alternate compiler with the existing five-scope RAII frame gave 13 differing main-body words for a hoisted-word for loop with the shared one variable, 13 with a literal 1 shift, 13 for a do/while with break, 15 with both word reads inline, and 13 with the previous-word compare first, against 10 for the existing goto candidate. The register assignment gap is unchanged: retail keeps the previous word in a0 and the current compare temporary in a1, the candidates swap them. The USA update stays retained assembly; no matched-C gain is claimed.

**Evidence:** docs/engine/material-contact.md; asm/Gap__Bec__beMatCtrl__vfunc_31.s; asm/Gap__Bec__beMatCtrl__vfunc_31.s; tools/verify.py

**Where:** 0x0039ec10; 0x0037c2c0; 0x0037c4c0 — Gameplay sound runtime - PLAY dispatch

The beSound message handler plays a named cue by looking up its beSoundData record and branching on _type: type 1 (music) returns without restarting when the name equals the current BGM, otherwise starts it in the stream player and records the name as the current BGM, and when the stream player returns 0 it enqueues a delayed PLAY retry; type 2 (ambience) starts in the stream player with the same delayed retry and no current-BGM record; every other type searches the playing-SE list for a row with the same record index and a deadline in the future and, if none, plays through the resident-effect player and stores a row with deadline now + 49,999,998 ns when a positive handle came back.

**Notes:** Read from the matched C++ of beSound::vfunc_34 (0x0039ec10, 3,792 bytes, byte-matched) and the matched stream/resident players: the repeat window applies to every type other than 1 and 2, is keyed by the record index in the info data list (not the name, not the channel) and stores only for handles above zero. PLAYatPAUSE (enum 3) sets beCri._pauseOnetime and then plays. The retail resident-effect pool is 52 handles: 4 streamed-ADX handles (created by FUN_0037d310 with mode 1, 24 kHz) for effects whose file is an ADX entry and 48 sound-bank handles (mode -1) for sound-bank effects, next to the BGM and ambience stream handles (mode 2, 48 kHz); a play request takes the first idle capable handle, and when none is idle it stops and reuses the handle with the lowest priority that is not above the new cue's priority, oldest first, or fails when no handle qualifies. ### #2766 · confirmed

**Where:** 0x003a6ce0; 0x003a6f70; 0x00281bb8 — Gameplay sound runtime - sound-bank backend boundary

The EE program does not interpret sound-bank sequences: starting a sound-bank cue and setting its level are commands sent to the sound IOP module through the RPC wrapper at 0x00281bb8 (play: command 1 with the handle id and the packed sequence number; volume: command 4 with the id and the level, 127 for effects), so the meaning of the event byte after the note, of the 00 82 02 element in WINDOW_OPEN2 and of the handle maximum lives in the IOP-side sound module, not in the EE code available here.

**Notes:** FUN_003a6ce0 validates the id (1..255), calls FUN_00281bb8(1, id, seq) and FUN_00281bb8(2, id, 0) and stores _req/_seq/_isPlaying in the beCriSndf object; FUN_003a6f70 for an audio type 3 voice calls FUN_00281bb8(7, id, 0) then FUN_00281bb8(4, id, level), while for ADX voices (types 1 and 2) it calls FUN_00332430, the ADX level path covered by the stream oracle. FUN_00281bb8 is retained as an asm body (308 bytes) of the RPC call into the CRI sound module; the IRX modules are on the disc under MODULES and are replaced, not analysed, by this project. Consequence: the event byte stays an unapplied recorded value and WINDOW_OPEN2 stays silent unless the IOP module is analysed; both are open items, not EE-code facts.

### #2767 · confirmed

**Where:** 0x003a7590; 0x003a7810; 0x003a7890; 0x0037cf30; 0x004c8fc0; 0x004c90b0 — Gameplay sound runtime - fades

A retail stream fade (VOLUMECTL2 name from to frames, VOLUMECTL UP/DOWN, and the 10-frame fade-out issued when a new music request finds the slot busy) is not linear: it arms a ramp that walks a 60-entry rising or falling ease table at (last - first) / frames table entries per frame, and each frame yields the level base + volume + (int)(210 * factor) - 210 in 0.1 dB units, ending as soon as that level reaches the target level and returning -999 (silence) when the target is 0.

**Notes:** FUN_003a7590 sets mode 3, from/to, the first and last table index (first index with from <= rising[i] or from >= falling[i]; last index with to >= rising[j] or to <= falling[j]) and step = (hi - lo) / frames; FUN_003a7810 adds the step and returns table[(int)position]; FUN_003a7890 turns the factor into the level, compares it with the level of the target value and clears the mode (returning -999 for a target of 0) when it is reached. The tables (0x004c8fc0 rising from 0.04, 0x004c90b0 falling from 0.96, both reaching their end value at index 53) are adjacent in memory, so a large step on a rising fade reads into the falling table. For a 10-frame fade to 0 the position is 5.9 * n, so the fade reaches silence on frame 9. The native ramp (port/src/ramp.c) equals the original instructions over 1,500 armed states and 39,952 frames, under the Emotion Engine FPU model of scripts/ee_core.py (rounding toward zero, assumed rather than measured); one step per 60 Hz frame is assumed from the 10-frame fades. The curve for resident (sound-bank) effects goes through the sound IOP module and is not covered.

**Evidence:** src/unmatched/FUN_003a7590.cpp; src/unmatched/FUN_003a7810.cpp; src/unmatched/FUN_003a7890.cpp; src/unmatched/FUN_0037cf30.cpp; port/src/ramp.c; port/tools/verify_ramp.py

### #2769 · confirmed

**Where:** 0x0039af10 — Typing the port-critical closure - pad data
