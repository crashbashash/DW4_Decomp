### #3897 · confirmed

**Where:** tools/eegcc_compile.py assembler_env; FUN_00286d28; FUN_002944f0

The 32-bit Sony `ee-as` (GNU assembler 2.10-ee-001003-1) copies an expanded macro over itself with an overlapping `memcpy`, in `md_convert_frag`: `memcpy (fixptr - old, fixptr, new)`, with old 4 and new 12 for a load from a label. glibc's SSSE3 `memcpy` gets that copy wrong at some alignments, so the first instruction comes out as the last one: `lui, addu, lw` becomes `lw, addu, lw`, or `ld` for a doubleword load. Which functions are hit depends on where the C library places the block, so results differed between systems from identical assembly. Disabling that `memcpy` with `glibc.cpu.hwcaps=-SSSE3` gives a full match even in a heap layout that otherwise breaks five functions, and `glibc.malloc.mmap_threshold=0` keeps blocks away from the bad alignment without removing the faulty copy. Native builds set both, with `-SSE2` as well so the choice does not depend on the CPU. A preloaded `memcpy` that calls `memmove` (docker/memmove_shim.c) gives a full match with neither setting, under a C library that otherwise fails, so the copy is the fault; the container uses it with the settings. `MALLOC_PERTURB_`, disabling tcache, an empty environment, the locale and disabling ASLR change nothing. Binutils for `mipsel-linux-gnu` is not involved.
