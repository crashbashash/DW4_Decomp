# The VU1 renderer's microcode map

_Generated by `scripts/vu1_microcode.py` -- do not hand-edit._

The VU1 assembler left its symbol table in the image: a `name;offset;...` string in rodata at `0x491910`, from `vu1_entry_UCODE_BEGIN;0` to `vu1_end_UCODE_END;109184`. It is the complete map of the renderer's microcode -- **237 entry points** over a **109184-byte** ucode image. The `p2` backend parses it once at runtime (`0x20d790`, splitting the string on `;` in place; the token base is kept at `0x57c2b0`), because the engine selects a program *by name* and jumps the VU1 to its offset. Many names share a start offset -- those are aliases, e.g. `LIGHT_SHARED` is the same code as `LIGHT_N_DIFFUSE_AMBIENT_DIRECTIONAL` -- and the ranges nest, the shared name being the outer envelope.

## Where the bytes are

The **microcode image is at `0x00467178`, 109184 bytes** (`0x00467178`..`0x00481bf8`), and it is verifiable without a VU disassembler. Two independent methods agree on the start: the image is **zero-filled from `0x00481bf8`** (so `start + 109184` is where the zeroes begin), and a per-8-byte VU-plausibility scan over the surrounding rodata peaks exactly there. What makes it microcode and not a coincidence is the content:

* **1483 NOP pairs in `(lower, upper)` order and 0 reversed** -- the canonical pair is `8000033c` (lower NOP) then `000002ff` (upper NOP);
* the lower-word opcode holds a real VU profile -- **LQ 12.1 %, ILW 8.8 %, IADDIU 4.8 %, ISUBIU 2.2 %, IBGTZ 231, JR 203, ISW 196, SQ 164, BAL 149, IBEQ 112, B 103, IBNE 98**;
* the upper word's opcode form is the `0x40+` *upper-only* marker for 61 % of the instructions, which is what a vector unit's code looks like;
* and the contrast test works: the same even/odd opcode asymmetry measure is **0.90 here against 0.076 in known EE code**, so the metric is not flattering everything.

It sits immediately after **a run of EE-side vfunc stubs**: `0x542a48` holds the pointers `0x466d00`, `0x466e00`, `0x466f80`, `0x4670b0`, `0x4670c0`, `0x4670d0`, `0x4670e0`, `0x4670f0`, `0x467100`, `0x467110` -- `jr ra` stubs whose last one ends where the microcode begins. **Whose table that is, is not established**: it is not an RTTI vtable in `data/vtables.json`, no `[rtti, 0]` header appears within `0x200` bytes before it, and the words just before the run are `igAdxAudio` vfunc values 16-19, so it may be a subclass's vtable rather than the renderer's. Treat the adjacency as a layout fact, not an attribution. Extract it with `scripts/vu1_microcode.py --elf <game.elf> --extract <out>` (the bytes are game data and are never committed).

For the four bits without a condition the set is still the answer, and reading it gives (the sets above are the evidence; these lines are the reading):

* `0x02000000` (22 programs) -- **the projected (MVPS) matrix is needed** -- the `TRANS_MVPS*`/`COMPRESS_*` set plus all four `VIEWPORT_KICK_END*` programs, which project and then kick
* `0x00400000` (12 programs) -- **primitive-specific clipping** -- the `CLIP_*` programs parameterised by primitive kind (`LINE`, `LINESTRIP`, `POINT`, `SPRITE`, `TRIANGLE`, `TRIANGLEFAN`, `TRIANGLESTRIP`, and their `_ARRAY`/`_CULLFACE` forms), as against the general clippers in 0x800000
* `0x00000800` (26 programs) -- **the model-view matrix is needed** -- every `TRANS_MV*` transform plus every `COMPRESS_*`; it is the weaker of the two MV bits (24 of the 26 also carry 0x40000)
* `0x00000080` (12 programs) -- the programs that light with **four infinite (directional) lights** -- every `INFINITE_4` program, and none of the `LIGHT_LOCAL_N_INFINITE_4_*` ones (which are 0x4000, positional, instead)
