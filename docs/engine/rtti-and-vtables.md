# RTTI, vtables and class names

How to get class and method names out of a **stripped** `game.elf`, and what that
yields today. This is the decompilation on-ramp: the binary has no symbol table,
so the only source of real names is the metadata the compiler emitted: RTTI
records, vtables, and the class reflection records.

Tooling: `scripts/dump_vtables.py`, `scripts/apply_vtable_names.py`,
`scripts/dump_reflection.py` + `scripts/apply_reflection_names.py` (class/MetaField
metadata; see [`reflection-metadata.md`](reflection-metadata.md)).
Output: `ghidra-projects/dw4/vtables.json`, `ghidra-projects/dw4/reflection.json`.

---

## 1. Why this exists

`game.elf` is stripped: `.symtab` is zero-length, there is no debug info, and
auto-analysis produced **15,167 functions of which 112 were named**, all PS2 SDK
syscall stubs. A stripped C++ binary *is* its vtable graph, and MWCCPS2 also
emits RTTI alongside every vtable, with the **class name as a rodata string**.
Recovering that graph is what turns `Gap__igMersenneTwisterRandomNumber__vfunc_13` into something readable.

Digimon World 4 was built with **Metrowerks CodeWarrior for PS2 2.4.1.01**
(see [`toolchain.md`](toolchain.md)), which is why the layout below is
Metrowerks-flavoured rather than Itanium C++ ABI.

## 2. The layout

Two adjacent rodata structures per class.

### `__RTTI__ClassName`: 16 bytes

```
+0x00  .4byte <ptr to class-name string>   e.g. 0x00508b30 -> "Gap::Bec::beGeneraterInfoWork"
+0x04  .4byte <base ref>                   0 for a root class; otherwise a pointer to a
                                           slot that itself holds the base class's __RTTI__ address
+0x08  .4byte 0
+0x0c  .4byte 0
```

The `+4` indirection is real: for `beGeneraterInfoWork` at `0x00508b60`, `+4` is
`0x00508b50`, and `*(0x00508b50) == 0x004ffe48` (the `igObject` RTTI record). The
class-name strings are full C++ identifiers (`Gap::Core::igObject`,
`Gap::Bec::beModelCtrl`, `Gap::Core::igTObjectList<Gap::Attrs::igTextureBindAttr>`
), so the **namespace and template arguments come for free**.

### `__vt__ClassName`: header plus vfunc array

```
+0x00  .4byte <ptr to __RTTI__ record>
+0x04  .4byte 0
+0x08  .4byte <vfunc 0>
+0x0c  .4byte <vfunc 1>
...
```

The array runs until the next `__vt__` header (`{rtti_ptr, 0}`), which is how the
slot count is recovered. Verified against the docs' live-RAM result:
`beGeneraterInfoWork`'s vtable is `0x00536050`, exactly the address recorded from
the running game.

Word +0 ties a vtable to its class: `beGeneraterData`'s vtable `0x00535eb0` reads
`0x005089c8`, the `rtti` value in `data/vtables.json`. A vtable whose +0 is zero
belongs to a class with no RTTI record. The MetaField classes are such classes, which
is why none is in the 478-entry dump ([RTTI-less vtables](#rtti-less-vtables-resolved-from-getvtable)).

### Inheritance, and the important catch

The `+4` field looks like the base class and is **not**. Measured across all 579
records: **578 point at `Gap::Core::igObject` and one is the root**
(`igObject` itself). So the field tells you every class derives from `igObject`
and nothing more: it carries **no immediate-base information**.

The real hierarchy cannot be recovered from the vtables either: intermediate
bases such as `Gap::Core::igObjectList` and the
`Gap::Core::igTObjectList<Gap::Attrs::...>` instantiations **have RTTI records but
no emitted vtable**. Vtable prefix sharing only ever exposes the ~20-slot
`igObject` prefix, so `beNDMWMdlEnemy` and `beNDMWMdlObject` are indistinguishable
from siblings.

Practical consequence: a shared vfunc body resolves to `igObject` and no deeper.
That names the global defaults correctly and cannot name group-specific ones.

**The hierarchy is recovered elsewhere.** The reflection registrar's
`a3` ("fn2") returns the *base* class's MetaObject and is passed straight to
`igMetaObject_InheritFromBase`, so parsing the getter's returned handle and mapping
it back through `data/reflection.json` yields the real parent of **1,074 of 1,075**
classes (`data/class-hierarchy.tsv`, regenerated by `scripts/gen_class_hierarchy.py`).
It does **not** resolve the ambiguous vfuncs below, though; see [§6](#6-what-the-census-also-found-open).

## 3. Census (game.elf)

| | |
|---|---|
| RTTI records | **579** |
| Classes with an emitted vtable | **478** |
| Total vfunc slots | **11,714** |
| Distinct functions reachable from vtables | **1,333** |
| of which, class overrides | 1,239 |
| of which, shared base defaults | 94 |
| **Uniquely named** (the 94 minus collisions; see below) | **1,286** |
| Ambiguous after the vtable pass | 47: 19 named from the hierarchy, 28 unnamed |
| Functions newly created (auto-analysis missed them) | 807 |
| Functions renamed | 526 |
| `__RTTI__` / `__vt__` labels | 1,045 |

All 478 RTTI-headed vtables sit in a tight region `0x00533738`–`0x00540b48`,
packed back to back. The vtable pass takes named functions overall from **112 of 15,167** to
**1,364 of 15,974**, and adds **807 functions** that auto-analysis
had merged or missed.

### Why 11,714 slots give only 1,333 names

MWCC emits **one shared default stub per slot** and points every non-overriding
class at it. `0x002ff0a0` is slot 0 of all 478 vtables; the defaults
`0x002ff0a0`–`0x002ff1c0` are 16-byte `jr ra` bodies. So the ~21-slot base prefix
of every vtable is a single set of ~21 functions. Any vtable slot holding an address
in `0x002ff0a0..0x002ff1c0` is therefore an inherited `igObject` default, not an
override.

Naming rule:

- referenced by **one** class → `<Class>::vfunc_NN` (`override`);
- referenced by **many** → the declaring class is the **most-derived common
  ancestor** of every referencing class, which, because of the [inheritance
  catch](#inheritance-and-the-important-catch), is always `igObject`, so the
  shared defaults become `Gap::Core::igObject::vfunc_NN` (`inherited`).

The name is an *address-derived* label, not the original identifier: it is
`Class::vfunc_<slot>`, which is the standard convention for unnamed virtuals.

### The 47 ambiguous bodies, 19 of them named

Several **distinct** bodies can resolve to the same owner + slot when the true
owner is an unnamed intermediate base. Example: slot 12 of 70 `*List` classes
resolves to `igObject::vfunc_12` for two different bodies: one shared by 408
classes (the true global default) and one shared by those 70 (an
`igObjectList`-level default whose owner has no vtable).

Two functions sharing one name is worse than an honest blank, so the widest
group keeps the name and the other 47 addresses carry default names with
a plate comment recording the slot, the referrer families and why.

The recovered hierarchy does let most of them be placed, but not by the lowest
common ancestor of the referrers, which is always `igObject`
 and says nothing; the right question is whether some class's
**descendant set** is *exactly* the referrer set. A body referenced by every
descendant of `C` and by nothing else is `C`'s slot, whether or not `C` emits a
vtable, and these owners are precisely classes that declare the virtual but
never emit a vtable (abstract bases), which is why the vtable pass misses them.

`scripts/seed_names_vfunc_defaults.py` applies the rule: candidate `C` is
accepted when `R ⊆ D(C) ∪ {C}` and `(D(C) ∪ {C}) \ R ⊆ {C}` (every referrer is a
descendant, and the only non-referrer in the closure is `C` itself), and only
when the candidate is **unique**. It places **19** bodies and writes them to
`config/SLUS-20836/names/Vtables.tsv` as `<Class>::vfunc_<slot>`, the same derived-label
convention as the other 1,286. The largest families: `igTransform` (slots 7, 24,
25, 28, 29: the `beCopyModelCtrl2`/`beCopyTransform`/`beModelCtrlNode2`/
`beTransformSync` family), `beModelCtrl` (25, 33), `beNDMWListCtrl` (22, 23, 24),
and single slots for `beBaseInfoManager`, `beBinDataObject`, `beSaveApi`,
`beNDMWMdlPEBase` (46, 47), `beNDMWMdlPEBaseInfoWork`, `beNDMWWindowSelect`,
`beNDMWWindowTitle` and `beNDMWStatusCtrlBaseEquip`.

The remaining **28** are genuinely ownerless in the available data. Their base is
a template instantiation (`igTObjectList<…>`, `igTDataList<…>`, `beNode`,
`beModelCtrlNode`) that has **no MetaObject**, so it is absent from the hierarchy
table and cannot be a candidate; the referrer set is a *superset*-closed family
(the 70 `*List` bodies, the 46–47 `*Info` bodies, the `beNode`/`beModelCtrlNode`
slot family) that no single hierarchy class's descendants equal. Naming these
would be a guess and they stay `FUN_`; the plate comments record each family.

### Residual duplicate names are thunks

Two logical functions each appear under one name twice because 4 of their entry
points are Ghidra **thunks** (`0x001b6ca0`, `0x001ce700`, `0x001d3390` → the
slot-8 stub; `0x002f0030` → the slot-0 stub). Ghidra keeps a thunk's name synced
to its target and **ignores renames of the thunk**, so this is expected, not a
bug in the tooling.

## 4. Running it

```sh
# 1. structure  ->  vtables.json  (read-only)
pyghidra-run orig/SLUS-20836/SLUS_208.36 \
    --project-path ghidra-projects/dw4 --project-name dw4 --no-analysis \
    -postScript scripts/dump_vtables.py \
    --out ghidra-projects/dw4/vtables.json

# 2. dry run (default): reports what would change, mutates nothing
pyghidra-run ... -postScript scripts/apply_vtable_names.py \
    --vtables ghidra-projects/dw4/vtables.json --report /tmp/vt.json

# 3. commit
pyghidra-run ... -postScript scripts/apply_vtable_names.py \
    --vtables ghidra-projects/dw4/vtables.json --apply --report /tmp/vt.json
```

`apply_vtable_names.py` is **idempotent** and only overwrites auto-analysis
placeholder names (`FUN_`, `thunk_FUN_`, `LAB_`, `SUB_`, `undefined*`, `DAT_`,
`PTR_`). A function carrying any other name is left alone and reported under
`kept_existing`, so hand analysis always outranks a derived name.

Back up the project before the first `--apply`: the DB is
`ghidra-projects/dw4/dw4/` (`dw4.prebak-20260922-2310` is the pre-naming
copy).

## 5. PyGhidra traps hit while building this

All of these fail *silently* or misleadingly; they are worth knowing before the
next script.

| Trap | Symptom | Fix |
|---|---|---|
| `for b in memory.getBlocks()` | loop body never runs | index it: `bl[i] for i in range(len(bl))` |
| `memory.getBytes(addr, bytearray(n))` | buffer stays **all zeros** | use `jpype.JArray(JByte)(n)` and mask with `& 0xFF` |
| Overlay blocks | image bounds become `0x0`–`hi` | keep only blocks whose address space is the **default** (`.comment`, `.reginfo`, `_elfHeader` are 0-based overlays) |
| Script exception | process exits **0** with no traceback | wrap `main()` and `traceback.print_exc()` explicitly |
| `FlatProgramAPI.createLabel` | `InvalidInputException: Symbol name contains invalid characters` | labels reject `<`, `>`, `*`, `,`; sanitise; `Function.setName` accepts them, so function and label names need different escaping |
| Renaming a thunk | `setName` silently does nothing | Ghidra syncs thunk names to their target; name the **target** and accept that thunks follow. Process non-thunks before thunks |

Note also that the merged ELF has **no sections to consult**: `.text` and
`.rodata` are one `WAX` block `0x00100000`–`0x00554aff`, so the code/rodata
boundary must be found empirically. `dump_vtables.py` takes the first 512-byte
window that is ≥95 % printable ASCII-or-NUL, which lands on `0x00483574` (the
last `jr ra` is at `0x00482958`).

## 6. What the census also found (open)

Two things fell out of the scan that are **not** vtables but matter.

### The class reflection records

Scanning for code-pointer runs in rodata finds 1,532 runs / 35,211 slots; 478 carry
the `{rtti, 0}` header (the vtables). The rest are mostly the **per-class field
tables** of the engine's reflection system: four parallel arrays of `[ctor][names]
[descs][offsets]`, one entry per field, driven by `igMetaObject_CreateFields` +
`igMetaObject_NameFields` from each class's registration init.

The full format, the registrar `igMetaObject_RegisterClass`, the field-type catalogue and the
extraction tool are documented in
[`reflection-metadata.md`](reflection-metadata.md); `scripts/dump_reflection.py`
recovers **1,075 MetaObjects, 659 with fields, 3,680 fields with name + offset +
type** (`data/reflection.json`).

Two further points: the class name is an argument at
the registrar call site (not adjacent in the data), and the `__ct`/`__dt`/`__as`/
`__eq` strings are a single MWCC name-mangling/operator lookup table at
`0x004fde68`, **not** per-class method names. The field tables do not name the 47
shared vfunc bodies; the 28 the hierarchy does not place (§3) remain open.

### RTTI-less vtables, resolved from `GetVTable`

58 runs of ≥5 code pointers (1,537 slots) in the vtable region
`0x00533000`–`0x00542000` carry a `{0, 0}` header. The **RNG class** is one: the
docs record its vtable as `0x0052B8E0`, its vfunc array starts at `0x0052B8E8`
with `{0, 0}`, and it contains `Reset` (`0x001E6B80`, slot 11) and `sgenrand`
(`0x001E6B20`, slot 21), so that class simply has no RTTI to name it from.

Layout alone cannot separate these from reflection records; a real test is
whether the table address is stored into an object's vptr (`object+0`) by a
constructor, or read by a virtual call site.

**The class of an RTTI-less vtable is nonetheless recovered.** Every class has a
`<Class>_GetVTable` function, and it builds the class's vtable as the first
rodata-range value stored to a stack slot, the same rule
[`seed_names_metafield_slots.py`](naming.md) uses for the MetaField subclasses
(`metafield-slots`). Applying it to **every** `_GetVTable` symbol
resolves **958 distinct vtables / 980 classes**, of which **499 are not RTTI
records**. The two sources are consistent (the class agrees on 453 of the 454
vtables they share; the one miss is a duplicate-handle class whose symbol carries
a `_587aa0` suffix), and for the shared vtables the generated
`Class::vfunc_N` equals the RTTI name **1197/1197**.

Reading a vtable out of `<Class>_GetVTable` has three traps, each of which silently
mis-attributes:

- **The first `lui`/`addiu` pair in the vtable range is not the answer.** The pair is
  often split, and every body also materialises its base class's vtable for an identity
  test, which gives 26 classes `igMetaField`'s table. Take the first rodata-range value
  actually stored to a stack slot, with registers tracked. 3 of 983 classes materialise
  it from a global and do not resolve.
- **Counting matching slots does not test descent.** The embedded `igObject` block
  (+0x08..+0x58) matches in every subclass. Count only the 18 named MetaField slots:
  25 classes score 16-18 and all others at most 4.
- **A body used by more than one class's vtable cannot be attributed.** Ten classes
  (`igIntMetaField`, `igBoolMetaField`, ...) share `igMetaField`'s vtable whole.

The generated `GetSize` overrides corroborate the rule by returning their element
sizes: Vec2f 8, Vec3f 12, Vec4f 16, Matrix44f 64.

So the RTTI-less vtables are not a blind spot: their unmatched unique slot
bodies are named `<Namespace>::<Class>::vfunc_N` by
`scripts/seed_names_getvtable_slots.py` in
`config/SLUS-20836/names/GetVTableSlots.tsv`, all `ig*` engine classes (no `be*`; the game's
classes all carry RTTI). The namespace is what retail strings give for the class, else what they
prove for its library in `config/SLUS-20836/regions.tsv`, else `Gap` alone (no retail string names
the namespace of the maths, Base, DataPump, WindowInput, Collision, Audio or SceneSearch classes). A
table ends where code loads the next table's address. A slot body used by more than one class's
vtable is a shared inherited default and is skipped, as is any body found in a resolved ancestor's
vtable. Where a body linked in another library than its class, it is an inline method kept from the
first file that used it, which always comes earlier in link order.

A `_GetVTable` builds a temporary object: its first table store is the class's own table, and any
later store is the destructor resetting the object to an ancestor's table. A body in such a table is
inherited, so its owner is the highest class holding it at that slot, provided every pointer to the
body in the image comes from that class's subtree. Those names are reviewed, not generated, and live
in `config/SLUS-20836/names/VtableOwners.tsv`.

Real tables run past the generator's 62 slots: call sites reach slot 261. For owner review a table
ends at two zero words (the next table's header), at a non-zero word that is not code, or at the next
known table. Inheritance is single, so sibling classes sharing a body prove their lowest common
ancestor holds it, unless that ancestor's own table has a different body at the slot. A body stays
unnamed when a pointer to it lies outside every resolved table, or when the ancestor's table
contradicts the siblings. The same generator emits the whole map:
`data/vtables-getvtable.json`, `{vtable: {class, vfuncs[62]}}` for the 498
non-RTTI vtables, cut at slot 62, regenerated by `scripts/sync_data.sh`.

## 7. Naming slots in local dummy-vtable views

A C++ unit that has to dispatch one virtual through the retail vtable declares a *local
view* with dummy virtuals in front of the one it calls:

```cpp
class igObjectSlotView {            // include/dw4/pool_slot.hpp
public:
    virtual void d0(); ... virtual void d28();   // 29 dummies
    virtual void vfunc_29();                      // the slot the manager calls
    unsigned int _refCount;
};
```

MWCC lays the vtable out as in [§2](#2-the-layout): `{rtti, 0}` then the slots, and the
object's vptr points at the header, so the **k-th declared virtual (0-based, dummies
counted) dispatches the word at `+0x08 + 4*k`**, which is exactly what the project's
names mean: `vfunc 0` is the word at `+0x08`, and `config/SLUS-20836/symbols.txt` /
`config/SLUS-20836/names/Vtables.tsv` call the body in slot NN `<Class>::vfunc_NN`. So a declared
virtual named `vfunc_NN` is honest only when **NN == k**.

A name that is off still produces the right bytes, because the dispatch offset comes
from the position, not the name: a `vfunc_31` declared as the 30th virtual reaches
the project's `vfunc_29`, and a `Player2Virt::vfunc_35` declared 34th reaches
`beNDMWMdlPlayer2`'s slot 33, which `data/vtables.json` resolves to
`Gap::Bec::beModelCtrl::vfunc_33`, the message handler the call passes `(Msg *, const
char *)` to. Byte identity does not catch such a name, so the rule is checked mechanically:

- `scripts/check_vtable_slots.py` parses every class/struct body that declares virtuals
  in `src/**/*.cpp` and `include/dw4/**`, and reports each `vfunc_NN` whose position
  k ≠ NN with file:line, the declared NN and the actual k. A class with a base is
  skipped (its slots start after the base's and are not knowable from the text) and
  listed with `--verbose`.
- `make vtable-slots-check` runs its unit test
  (`testing/test_check_vtable_slots.py`) and the script, and fails on any hit.

When writing such a view: name the dummies anything but `vfunc_NN`, number the real
slot by its position, and say in the comment which `<Class>::vfunc_NN` it reaches.
